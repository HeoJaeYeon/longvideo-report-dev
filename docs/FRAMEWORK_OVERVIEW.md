# Part 1. 거시적 설명: 무엇을 어떻게 이어 붙였나

## 1.1 목표와 출발점

- **목표**: 장편 영상에 대한 질의를 받아 보고서 목차(outline)를 짜고, 섹션마다 영상 메모리에서 근거를 검색해, **문장마다 근거(시간·프레임)가 연결된 보고서**를 만든다.
- **출발점이 된 두 시스템**
  - **WorldMM**: 장편 영상 QA 시스템. 영상을 세 종류의 메모리로 만들어 두고, 에이전트가 검색과 답변을 반복한다.
    - episodic: 10sec / 30sec / 3min / 10min 캡션과 granularity별 HippoRAG 지식그래프
    - semantic: 영상 전체에서 뽑아 통합한 triple
    - visual: 10초 구간 비디오 임베딩(VLM2Vec)
  - **Deep-Reporter**: 웹 문서로 근거 인용 장문 보고서를 쓰는 시스템. planner → [검색어 생성 → 검색 → 섹션 작성] × 섹션 수 → 합치기.
- **핵심 아이디어**: Deep-Reporter의 "검색" 자리에 웹 대신 **WorldMM 영상 메모리**를 꽂고, 프롬프트와 출력 처리를 영상 보고서에 맞게 바꾼다.
- **1차 대상**: Video-MME long 50개 영상(WorldMM 메모리 구축 완료). 관제(surveillance) 영상은 그다음이다.

## 1.2 설계를 결정한 제약

| 제약 | 설계에 준 영향 |
|---|---|
| 기존 repo(WorldMM, Deep-Report, MERIT) **코드 수정 금지** | 파일을 고치지 않고 HTTP로 연결했고, 동작을 바꿀 때는 실행 중에만 교체한 뒤 되돌린다 |
| LLM은 **로컬 Qwen3-VL-8B 기본**, OpenAI 경로 보존 | LLM 서버를 OpenAI 호환 API로 만들고, 설정(`llm.backend`)으로 바꾼다 |
| **LLM 호출이 많은 무거운 설계 금지** | WorldMM 원본 검색(질의당 최대 5회)을 그대로 쓰지 않고, 요청당 1회인 L1 방식을 만들었다 |
| GPU는 허용된 4–7번만, 프로세스당 20GB 미만, 기존 작업 중단 금지 | 모든 GPU 프로세스에 19,000 MiB 상한을 건다. LLM과 임베딩 모델을 다른 프로세스로 나눈다 |
| 출력은 근거를 검증할 수 있어야 함 | 후처리기, 규칙 근거 검사, 사후 검증을 새로 만들었다 |

## 1.3 전체 구조

```

   캡션 4종, 10sec OpenIE, semantic, visual 임베딩     (HippoRAG 그래프를 미리 구축)

[실행 중인 서비스 2개, GPU]

 ★videorag_retriever_service.py :8020   Deep-Reporter 검색 계약을 구현한 WorldMM 검색 서버

[보고서 1건: ★run_report.py, CPU, 모델 로드 없음]
 ① 설정·사전 확인

 ③ ★domain_templates.py: Deep-Reporter 프롬프트 3개와 앞 섹션 맥락 함수를 실행 중에만 교체
 ④ Deep-Reporter 그래프(원본 코드 그대로)
      planner → [query 생성 → search ──HTTP──▶ 검색 서버 → section writing] × 섹션 수 → combine
 ⑤⑥ ★grounding_postprocessor.py: 인용 → 참조 번호·그림, 규칙 근거 검사, 이미지 시간 기록
 ⑦ 사후 검증(조용한 실패 감지)
 ⑧ ★report_translator.py: 한국어 번역본

```

## 1.4 이어 붙인 지점 3곳

| 접점 | 방법 | 이유 |
|---|---|---|
| **① 검색** | Deep-Reporter의 `retriever_url`(HTTP)에 우리 검색 서버 주소를 넣는다. 요청 `{query_list, type, topk}`와 응답 형식은 Deep-Reporter 계약을 그대로 따른다. 요청 본문에 영상 id가 없어서 URL(`/videos/<vid>/search`)에 넣었다 | Deep-Reporter 코드를 고치지 않고 연결할 수 있는 공식 지점이다. 실행 환경이 분리되고, 나중에 MERIT으로 바꿀 때 주소만 바꾸면 된다 |
| **② LLM** | Deep-Reporter는 키·URL을 **환경변수로만** 받는다(설정 dict로 넘기면 버려지는 것을 실측). `run_report.py`가 환경변수를 설정하고, 실제로 연결된 주소가 기대값과 같은지 확인한 뒤 실행한다 | 기존 설계안의 "`openai_base_url`만 바꾸면 로컬 전환"은 실제로 `Missing credentials` 오류가 났다 |
| **③ 프롬프트와 동작** | Deep-Reporter 노드가 매 호출마다 읽는 전역 변수(템플릿 3개, `_update_context` 함수)를 `with` 블록 동안만 바꾸고 끝나면 되돌린다. 바꾸기 전에 계약(placeholder, 시그니처 등)을 검사한다 | 원본 프롬프트는 웹 리포트용이다(이미지 질의가 "차트, 다이어그램", 타임스탬프 개념 없음). 파일 수정이 금지돼 있다. 검사가 실패하면 웹 프롬프트로 몰래 돌아가지 않고 실행 전에 멈춘다 |

# Part 2. 세부 설계와 그 이유

## 2.1 사전 인덱싱 (`prebuild_episodic_index.py`)

- **무엇**: 영상마다 granularity 4개의 HippoRAG 지식그래프를 미리 만들어 디스크 캐시로 저장한다.
- **왜 필요한가**
  - HippoRAG는 그래프를 만들 때 청크마다 LLM을 2회(NER, triple) 부른다.
  - 검색 서버가 실행 중에 이걸 하면 보고서마다 수백 번 LLM을 부르게 된다.
  - 한 번 만들어 두면 서버 시작 시 LLM 호출은 0회다(캐시 재사용 동작을 코드로 확인).
- **비용을 줄인 방법**
  - WorldMM 전처리 때 만든 10sec OpenIE 결과(12,551개)를 "시드"로 넣는다. 해시 방식, OpenIE 클래스, 모델이 모두 같다는 것을 확인했다.
  - 50개 영상 기준 LLM 호출이 **약 35,400회 → 12,818회**로 준다(dry-run 실측). 아래 긴 청크 분할을 넣은 뒤로는 13,424회다.
  - 빈 triple 1,252개는 원래 비어 있던 것인지 오류였는지 구분할 수 없어 시드에서 빼고 다시 계산한다.
- **GPU 문제와 결정 1(A안)**
  - 원래 방식은 LLM(약 17.9GB)과 임베딩 모델(약 7.7GB)을 한 프로세스에 올려 GPU당 20GB 규칙을 넘는다.
  - 그래서 OpenIE를 **LLM 서버에 HTTP로 보내고**, 인덱서는 임베딩 모델만 올린다.
  - 결과가 기존과 같도록 맞춘 점: 같은 메시지, `max_tokens=2048`, 샘플링 인자 없음, 같은 JSON 파서, 같은 재시도 깊이(코드로 확인).
  - LLM 서버를 여러 개 띄워 돌아가며 요청을 보내므로 병렬 처리도 된다.
  - 실행 스크립트: `run_prebuild_http.sh <LLM_GPUS> <INDEXER_GPU>`. GPU를 다른 사용자와 같이 쓸 때는 실행 전 여유 확인·실행 중 감시·자동 중단이 있는 `experiments/gpu_3videos.py`.
- **긴 청크 분할 OpenIE (2026-10-22 추가)**
  - 문제(실측): 10min 청크(중앙값 1,373토큰)의 OpenIE 출력이 2,048토큰 상한을 넘어 JSON이 잘렸다. 파서가 잘린 응답을 통째로 버리고 청크당 최대 15회(5 × 3) 재시도해, 영상 2개째에서 진행이 멈춘 것처럼 보였다. 넘는 출력은 같은 (주어, 술어)에 목적어만 바꿔 39–115회 나열하는 **열거 폭주**와, 반복은 없지만 긴 **정상 출력** 두 가지였다. 입력이 1,025토큰 이하인 호출 333회에서는 잘림이 0건이었다.
  - 반복 억제 같은 디코딩 설정 변경은 비교 실험에서 효과가 없거나 원인 불명의 이상이 있어 쓰지 않았다.
  - 해결: 1,100토큰을 넘는 청크는 문단 단위 700토큰 이하 조각으로 나눠 OpenIE를 돌리고 청크 단위로 합친다(그래프 구조는 그대로). 안전장치로 파싱에 실패한 응답의 완성된 항목만 살리고, 연속 15개를 넘는 폭주 triple은 버린다. CPU 테스트(실제 실패 응답 14건 구제)는 통과했고, GPU 효과는 미검증이다.
  - 같이 발견한 것: 10min 캡션 232개 중 32개(20영상)가 전처리에서 2,048토큰에 잘려 있다(재생성 보류).

## 2.2 LLM 서버 (`local_llm_server.py`)

- OpenAI 호환 `/v1/chat/completions`. 내부는 WorldMM의 검증된 Qwen3-VL-8B 래퍼다.
- **왜**: vLLM이 설치돼 있지 않았고, 새 패키지 없이 바로 쓸 수 있는 방법이었다. 같은 주소로 나중에 vLLM으로 바꿀 수 있다.
- 하나의 서버를 Deep-Reporter, L1 필터, 번역, 사전 인덱싱이 함께 쓴다.

## 2.3 검색 서버 (`videorag_retriever_service.py`)

### L0 / L1 / full (LLM 비용 문제를 푼 핵심 설계)

| 모드 | 검색 LLM 호출 | 설명 |
|---|---|---|
| full | 질의당 최대 5회 | WorldMM 원본(granularity 4개 × DSPy 필터 + multiscale 필터 1회) |
| **L1 (기본)** | **검색 요청당 1회** | DSPy 필터만 빼고 그래프 검색 후보를 모은 뒤, 섹션의 모든 질의 후보에 multiscale 필터를 1회 적용 |
| L0 | 0 | 규칙(후보 수 상한 + 순위 병합)만 |

- **L1을 고른 이유**: 처음에는 L0(0회)를 제안했다. Deep-Reporter 논문에서 근거 필터를 빼면 품질이 크게 떨어진 결과(Section Content 41.7 → 27.6)가 있어서, 최소 1회 필터를 남기는 L1로 바꿨고 사용자가 확정했다.
- **비용 비교**: 원본을 그대로 연결하면 5섹션 보고서에 LLM 약 86–136회, 현재 설계로는 16회(1 + 3×섹션 수)다.

### 그 밖의 설계
- **병합은 순위 기반(RRF)**: WorldMM 검색은 점수를 돌려주지 않고, 출처별 척도도 달라 점수로 합칠 수 없다.
- **근거 라벨**: writer가 근거의 종류와 시간을 알 수 있게 내용 앞에 붙인다.
  - `[00:00:40-00:00:50 | episodic 10sec]`
  - `[video-level knowledge | semantic]`: semantic은 시간 근거가 없어서 시간을 붙이지 않는다. WorldMM이 consolidation 단계에서 근거를 버리는 것을 코드로 확인했다.
  - 이미지: 구간 중앙 프레임과 같은 시각의 10sec 캡션
- **캐시 완전성 검사(409 거부)**: HippoRAG OpenIE는 LLM 오류를 삼키고 빈 결과를 캐시에 저장한다. 불완전한 캐시를 몰래 쓰지 않도록 로드 전에 검사한다.

## 2.4 템플릿 교체 (`domain_templates.py`)

| 템플릿 | 핵심 지시 | 이유 |
|---|---|---|
| **planner** | 영상의 **10min 캡션 개요(타임스탬프 포함)**를 넣고, 영상에 실제로 있는 내용으로만 3–6개 섹션, 마지막은 `Conclusion:` 결론 섹션 | 원본 planner는 영상 내용을 모르고 질의만 봐서 근거 없는 섹션을 만들 위험이 있다. 개요는 이미 있는 캡션이라 추가 LLM 호출이 없다 |
| **query** | text는 사건·인물 키워드, image는 "장면이 어떻게 보이는지" 묘사 문장 | 이미지 검색(VLM2Vec)은 텍스트→영상 유사도라 묘사형 질의가 맞다. 원본은 "차트, 다이어그램"을 요청한다 |
| **writer** | 근거에 있는 사실과 시간만, semantic에 시간 금지, 근거 없으면 없다고 쓰기, 시간순, 규칙 4(`[citation:imgN]` 금지), 규칙 6(반복 금지), 결론 100–250단어 | 근거 기반 영상 보고서용 지시 |

- **섹션 상한 6, 허용 범위 3–15**: Deep-Reporter는 그래프 반복 한도(`recursion_limit=50`) 때문에 **16섹션부터 보고서 전체가 사라진다**(실측, 15는 성공). 범위를 벗어난 값은 실행 전에 막는다.
- **계약 검사**: placeholder는 Deep-Reporter 노드 소스에서 AST로 직접 추출하고, 필수 문구와 `.format()` 시험 실행까지 확인한다.

## 2.5 앞 섹션 맥락 교체 (C0)

- **발견한 사실**
  - 논문은 앞 섹션을 "recursive summary"로 넘긴다고 하지만, 코드는 "섹션 설명 + 본문 앞 100자"이고 그 100자는 대부분 제목 줄이다.
  - 보고서 B로 복원해 보니, 결론을 쓰는 단계는 planner가 미리 써 둔 설명만 받았다.
  - Deep-Reporter에는 생성 뒤 보고서 전체를 다듬는 refine 단계도 **없다**(코드·논문 확인).
- **수정**
  - 앞 섹션의 제목과 단락 첫 문장(인용 번호 제거, 최대 3,600자)을 넘기도록 실행 중에만 교체한다. LLM은 쓰지 않는다.
  - 인용 번호를 지우는 이유: 앞 섹션의 번호는 그 섹션의 근거 목록을 가리켜서, 현재 섹션 근거와 섞이면 잘못된 인용이 생긴다.
- **채택하지 않은 대안**
  - 보고서 전체를 LLM이 다시 쓰기: 섹션별 근거 번호와 검증 체계가 깨진다.
  - `repetition_penalty`: 프롬프트 토큰까지 벌점을 줘서 근거의 이름·시간을 그대로 옮겨 쓰는 것을 막는다.
  - `no_repeat_ngram_size`: 프롬프트를 포함한 n-gram을 금지한다.

## 2.6 후처리기·근거 검사 (`grounding_postprocessor.py`)

- **인용 변환**
  - 섹션별 `[citation:txt3]` → 보고서 전체 번호 `[n]` + References(시간 구간).
  - 이미지는 프레임을 복사해 그림과 캡션으로 넣는다.
  - 잘못된 형식 `[citation:imgN]`도 그림으로 바꾼다(결정 3).
- **규칙 기반 근거 검사(결정 2)**
  - 문장의 따옴표 문구, 숫자, HH:MM:SS가 **그 문장이 인용한 근거**에 실제로 있는지 대조한다. LLM은 쓰지 않는다.
  - LLM 검증을 쓰지 않은 이유: 섹션마다 호출이 늘고, 같은 8B 모델이 검증해 신뢰도에 한계가 있다.
  - 보고서 A 대조 결과: 지적 9건 중 7건이 실제 오류(정밀도 약 78%).
- **부정 절 처리**: "근거에 X가 보이지 않는다" 절 안의 토큰은 검사에서 뺀다.
- **이미지-텍스트 시간 차이 기록**: 그림 프레임 시각과 인용된 텍스트 근거 구간 사이의 거리를 남긴다.

## 2.7 실행·검증 (`run_report.py`)

- **왜 필요한가**: Deep-Reporter는 실패해도 `success=True`로 끝나는 경로가 코드에 있다.
  - planner 파싱이 실패하면 섹션 1개로 몰래 대체된다.
  - LLM이 실패하면 본문에 `"Call failed"` 문자열이 들어간다.
  - 검색이 실패하면 근거 0건으로 계속 진행된다.
- **결과 판정**

  | 결과 | 조건 |
  |---|---|
  | exit 2 | 사전 확인·설정 실패. 생성하지 않는다 |
  | exit 1 | 검증 오류(위 실패들, `[?]`, 프레임 누락). 산출물은 저장한다 |
  | 경고 | 결론 규칙 위반, 근거 검사 지적 등 |

## 2.8 번역 (`report_translator.py`, 결정 6)

- 영어 보고서를 정본으로 두고, 섹션 단위로 한국어 번역본을 추가한다.
- 인용 번호, 시간, 따옴표 문구, 그림, 고유명사는 자리표시로 감췄다가 그대로 되돌린다.
- 자리표시가 깨지면 1회 재시도하고, 그래도 실패하면 영어 원문을 유지한다. 한자·가나가 섞여도 1회 재시도한다.
- 번역이 실패해도 영어 결과와 exit 코드는 바뀌지 않는다.

# Part 4. 남은 일과 꼭 알아야 할 한계

## 4.1 결과 해석에 직접 영향을 주는 사실

1. **4개 단위 사전 인덱싱 캐시는 검증 영상 3개만 있다**(2026-10-25 C-1, GPU 4–7, 27.4분, 호출 430회). 나머지 47개 영상은 아직 만들지 않았다.
   - 4개 단위 캐시로 검색(C-3: 요청 36건 성공, L1 text 4.4–7.9초)과 보고서 생성(C-4 3건, C-5 8건, 모두 exit 0·검증 `passed`)을 했다(`DESIGN_AND_STATUS.md` §9.12–§9.14). 그러나 **보고서 품질 문제가 남아 있다**: writer가 같은 문장을 8,192토큰까지 되풀이하는 루프(C-5 8건 중 2건), 구간 요약의 "the video closes"를 영상 결말로 옮김, 섹션 시간 순서 뒤집힘·화자 뒤바뀜, 번역 실패 17섹션 중 5개. 검증은 이 문제들을 잡지 못했다.
   - OpenIE는 샘플링 생성이라 같은 입력을 다시 계산하면 triple 집합이 크게 달라진다(Jaccard 0.2–0.3, C-2).
   - 10min 캡션 일부(20영상, 32개)는 전처리에서 잘려 있어, 다중 단위 캐시를 만들어도 그 부분의 내용은 빠진다.
2. **표본이 매우 작다.**
   - 4개 단위 보고서는 영상 3개, C-4 영상당 1건과 C-5 조건당 2회(영상 2개)뿐이다. C0(결정 4) 효과는 4 대 4로 확인되지 않았다.
   - 생성은 샘플링이라 같은 조건에서도 결과가 달라진다. A와 B의 차이를 모두 개선 효과로 볼 수 없다. 예: B에서 반복이 줄어든 것은 반복 방지 기능을 넣기 **전**이라 수정 효과가 아니다.
3. 테스트 캐시는 전처리의 빈 triple 18개까지 그대로 넣어 만들었다. 정식 인덱싱 결과와 다를 수 있다.
4. **최신 기능의 실제 실행 결과가 기대와 다르다.**
   - 규칙 6·C0·부정 절 처리·이미지 시간 기록·번역 한자 감지·이름 보호를 C-4·C-5에서 처음 실제 모델로 돌렸다.
   - 반복은 단락 유사도로 보면 B보다 낮았지만 writer 루프는 막지 못했고, C0의 효과는 확인되지 않았고, 번역은 B(보완 전, 6/6)보다 나빠졌다(12/17).
5. **"인용이 있다 ≠ 근거로 뒷받침된다."**
   - 규칙 검사는 숫자·따옴표·시간만 확인한다. 장면을 잘못 연결한 서술은 잡지 못하고, 재현율은 측정하지 못했다.
   - 현재 보고서는 **사람 검수 없이 믿을 수 있는 수준이 아니다.**
6. 그림이 해당 문장의 장면과 맞는지 사람이 확인하지 않았다. B에서는 텍스트 근거와 최대 1,015초 떨어진 프레임도 인용됐다.
7. **품질 평가를 시작하지 않았다.** Video-MME 문항 풀이 비교와 사람 검수 모두 미실시다.
8. L0/L1/full의 품질 차이는 측정하지 않았다(C-3은 지연과 단위 구성만 측정). L1이 품질을 얼마나 유지하는지는 아직 근거가 없다.

## 4.2 구현상의 알려진 한계

- **결론 섹션의 구조적 한계**: 결론도 자기 근거를 새로 검색하므로, 앞 섹션의 사실을 올바르게 인용할 수단이 없다. C0로 줄어드는지 측정해야 한다.
- **L1 필터 표시**: LLM 응답 형식이 깨져 RRF로 채워져도 `llm`으로 표시된다.
- **빈 triple의 "완료" 판정**: OpenIE가 재시도 후에도 실패한 청크는 빈 triple인데도 "완료"로 판정된다. 완료 표식에 빈 결과 수를 기록하고, 응답 구제로 줄 것으로 기대한다(미측정).
- **분할 OpenIE의 한계**: 조각 경계를 넘는 문맥을 잃을 수 있고, 분할 기준(1,100토큰)과 폭주 절단 기준(연속 15개)은 작은 표본에서 정한 경험적 값이다. 응답 구제·절단은 HTTP 경로에만 적용된다.
- **부정 절 처리의 빈틈**: 부정 절 안에 틀린 값이 전제로 들어간 경우("does not confirm the progression from 0/1 to 3/16")는 검사에서 빠진다.
- **이름 보호의 한계**: 이름 인식 모델(NER)이 없어 제품 이름도 영어로 남고, 문장 첫머리에만 나오는 이름은 보호되지 않는다.
- **시간 비용**: 보고서 1건에 B 기준 494초(생성 262초 + 번역 232초)가 걸렸다. 4개 단위와 C0를 쓰면 프롬프트가 길어져 더 걸릴 수 있다(미측정).
- **미검증 경로**: OpenAI 경로, vLLM 교체, 여러 영상을 연속으로 처리할 때 검색 서버의 영상 교체.

## 4.4 보고할 때 같이 밝혀 둘 사실

- 첫 GPU 검증 일부(캐시 생성, L0)는 "GPU 4–7 사용" 지시를 받기 **전에 GPU 0**에서 실행했다. 20GB 미만이었고 끝난 뒤 원래 사용량으로 돌아왔다.
